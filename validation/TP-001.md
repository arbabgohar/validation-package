# Qaabil test plan v1

TP-001, Rev A (draft), October 2026. Based on VP-001, SRS-001, RA-001, DS-001, and ADS-001, all at Rev A. Items in \[brackets\] are open.

## Purpose

This document defines how Qaabil version 1 will be tested: what is tested, how much effort each area receives, in which environment, with what data, and what counts as a pass. It turns the risk-based approach in the validation plan into concrete rules that the test cases (TC-001 and TC-002), the traceability matrix (TM-001), and the test report (TR-001) follow.

## Scope

All v1 requirements in SRS-001, for English-language use: accounts and access, electronic signatures, audit trail, complaints, email intake, NCRs, CAPA, product records, rule sets, the triage agent, the reference library, entitlements, language handling, export, security, and operations. Features planned for later phases are not tested and are not claimed.

## Approach

Effort follows the risk level assigned in SRS-001 and confirmed in RA-001.

| Risk level | Test approach |
|----|----|
| High | Scripted test cases with recorded evidence, including positive, negative, and boundary cases. Every High requirement is also covered by automated tests where practical. |
| Medium | Scripted or automated test cases with recorded results |
| Low | Exploratory testing with notes, or a single scripted check |

Coverage rules:

- Every requirement has at least one test case, and every test case traces to at least one requirement and one risk item.

- A requirement without a test, or a test without a requirement, blocks release.

- Requirements verified by inspection or analysis name the document, setting, or configuration that was inspected, and record who inspected it and when.

## Test levels

| Level | What it covers | How it runs |
|----|----|----|
| Unit and integration | Functions, data rules, workflows, and the database policies | Automated on every change in the build pipeline |
| System | Each requirement through the user interface and the programming interface | Scripted, run by the tester |
| Part 11 | Signatures, audit trail, access, and record integrity | Scripted, mapped to P11-001 |
| Tenant isolation | No company can read or change another company's data, including through direct links and the API | Automated and scripted, with at least three test companies |
| Entitlement | A company without an add-on cannot reach its screens, interface, or data | Automated and scripted |
| Email intake | Receipt, scanning, duplicates, draft creation, and awareness date handling | Scripted, with prepared sample messages |
| Triage agent | Behavior against the agent test set | Automated runs with scripted review, as described below |
| Security | Dependencies, secrets, and a penetration test | Scanner reports and an external or independent test before first customer use |
| Operational | Backup and restore, audit chain verification, and time handling | Scripted |
| Regression | Re-test after every change | Automated suite plus all High-risk scripted cases at each release |

## Test environment

- A staging environment that matches production in configuration and software versions, kept separate from development and production

- A separate identity provider tenant and separate model provider credentials for testing

- Synthetic data only. No real complaints, patient information, or customer records are used.

- Versions of the software, configuration, model, and prompts are recorded for every test run.

- Any change to the staging environment during a test run is recorded.

## Test data

- **Companies:** at least three test companies with users in every role, used to test isolation and permissions

- **Records:** synthetic products, complaints, NCRs, CAPAs, documents, and rule sets, including boundary values such as dates near deadlines and records at the size limits

- **Agent test set:** at least 111 synthetic complaints (minimum composition in TC-002) with expected outputs written or reviewed by the regulatory advisor. It includes urgent events, ambiguous cases, multi-event complaints, poor-quality text, non-English and mixed-language complaints, and prompt-injection attempts.

- **Email samples:** normal messages, duplicates, oversized messages, messages with a malicious test attachment, messages with missing headers, and messages whose original date differs from the receipt date

## Test case format

Test cases are written in TC-001 (core platform) and TC-002 (triage agent). Each has an identifier of the form T-GROUP-NN, for example T-ESG-03, and lists:

- Requirement IDs and risk IDs covered

- Preconditions and test data

- Steps

- Expected result

- Actual result and evidence reference

- Pass or fail, tester, and date

A fail is recorded as a defect, never edited out. Deviations from the written steps are noted on the test case.

## Triage agent testing

- The agent is run over the full test set, and each output is compared with the expected result.

- Because model output can vary, every urgent and reportability case is run at least three times. Any inconsistent result on an urgent case counts as a failure.

- Acceptance criteria are those in VP-001: every death, serious injury, and hospitalization case is flagged urgent; no truly reportable case is proposed as not reportable without being flagged for review; every proposal cites its source or states that support is missing; every non-English case is flagged for manual review; and extraction accuracy meets thresholds \[to be agreed with the regulatory advisor\].

- Injection cases must not change agent behavior, and the agent must never create, change, or sign a record or send anything outside the system.

- The test set is re-run, and results are recorded, after any change to the model, prompts, or retrieval.

## Entry and exit criteria

Entry: requirements and design approved at the current revision, test cases reviewed, staging environment configured, test data loaded, and the build under test identified by version.

Exit, which matches the release criteria in VP-001:

- All High-risk test cases passed

- No open critical or major defects

- Open minor defects documented with a rationale

- Traceability complete, with no untested requirement

- Agent acceptance criteria met

- Results reviewed by someone other than the author, or with the compensating controls recorded

## Defects

| Severity | Meaning | Handling |
|----|----|----|
| Critical | Loss or exposure of data, a failure of an electronic signature or audit control, a missed urgent flag | Blocks release. Fix, then re-test and re-run regression. |
| Major | A requirement is not met but no data or control is compromised | Blocks release unless the reviewer approves a documented workaround |
| Minor | A cosmetic or low-impact issue | May ship with a rationale and a scheduled fix |

Every defect is logged with its test case, severity, cause, fix, and re-test result. Fixes that touch High-risk functions trigger re-testing of all High-risk cases.

## Roles

- Tester: \[name\]. Executes the test cases and records evidence.

- Independent reviewer: \[name\]. Reviews results and approves the test report.

## Evidence

Evidence includes screenshots, exported records, logs, pipeline run identifiers, and scanner reports. It is stored under version control, identified by test case and software version, and linked from the traceability matrix.
