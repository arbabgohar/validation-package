Rev A (draft), October 2026. Based on the Qaabil software requirements specification, Rev A. Items in \[brackets\] are open.

## Purpose

This document describes how Qaabil version 1 is built so that it meets the software requirements. It records the architecture, the technology choices, the data model, and the design of the controls that matter most to regulated users: company separation, electronic signatures, the audit trail, and the triage agent. Testers, reviewers, and customers use it to understand why the system behaves as it does.

## Scope

This specification covers the v1 functions only, for English-language use: accounts and access, electronic signatures, audit trail, complaints, NCRs, CAPA, reportability rule sets, the triage agent, the reference library, entitlements, export, and the security and operational controls around them. Later phases will have their own design documents.

## Design principles

- **One deployable application.** A modular monolith keeps the system simple to test, release, and validate.

- **Separation by default.** Every record belongs to one company, and the database itself enforces that boundary.

- **Audit by default.** Changes to regulated records cannot happen without an audit entry written in the same transaction.

- **Agents propose, people decide.** The agent has read-only access and cannot change records.

- **Rules before models.** Deterministic checks run first and cannot be overridden by model output.

- **Configuration over code for regulation.** Reportability criteria and deadlines live in versioned rule sets, not in application code.

## Architecture

Qaabil has five layers. Requests flow from users and inputs, through the modules and the agent layer, to human review and signature, and finally into storage.

| Layer | Components | Responsibility |
|----|----|----|
| Inputs | Web interface, intake form, forwarded email address | Bring complaints, documents, and user actions into the system |
| Core modules | Complaints, NCR, CAPA, product records, reference library, rule sets | Workflows, validation of fields, and status control |
| Agent layer | Triage pipeline and the external model provider | Produce proposals for review |
| Control layer | Review, e-signature, permission checks, audit writer | Turn approved proposals and edits into records |
| Data layer | Relational database, file storage, audit log | Persist records, evidence, and history |

## Technology choices

| Area | Choice | Notes |

| Backend language and framework | Python with FastAPI | Typed request and response models |
| Data validation | Pydantic | Validates every request and every agent output against a strict schema |
| Database | PostgreSQL | Row-level security, JSON columns, and vector search for document retrieval |

## Company separation and routing

- **Subdomains.** A wildcard DNS record sends every company subdomain to the same application. The application reads the subdomain, finds the company, and rejects unknown names.

- **Row-level security.** Every table that holds company data carries a company identifier. For each request the application sets the current company in the database session, and database policies allow only rows that match. A missing or mismatched company returns no rows.

- **Defense in depth.** Permission checks also run in the application on every request, so a mistake in one layer does not expose data.

- **Domain claims.** A company administrator proves control of an email domain through a verification step. Public consumer domains are blocked. People with a verified email in a claimed domain can request to join, and the administrator sets whether they are admitted automatically or after approval.

- **Vendor access.** Support staff have no standing access. Access is granted for a limited time, approved by the customer, and logged.

## Data model

The diagram shared earlier is the starting point. These are the v1 entities.

| Entity | Key contents | Notes |
|----|----|----|
| Company | Name, subdomain, plan | Root of all tenant data |
| Domain claim | Company, domain, verification state | One company per domain |
| User and membership | Identity, company, role, active state | Deactivated users are kept for history |
| Product | Name, version, UDI, intended use, markets, classification | Complaints and CAPAs attach to products |
| Complaint | Product, awareness time, event details, status, reportability decision | Sequential numbers that are never reused |
| NCR | Description, lot, disposition, status | Linked to complaints and CAPAs |
| CAPA and CAPA action | Problem, root cause, actions, effectiveness check, status | Many complaints can link to one CAPA |
| Rule set and rule set version | Market, criteria, deadlines, effective date, approval | Each decision stores the version used |
| Reference document | Title, version, effective date, status | Only current approved versions reach the agent |
| Agent suggestion | Record, agent name, model version, prompt version, content | Stored separately from the record it concerns |
| Review decision | Suggestion, reviewer, decision, reason | Accept, edit, or reject |
| Signature | Signer, meaning, time, record version, content fingerprint | Immutable |
| Audit event | Actor, action, record, before and after values, time | Append-only |
| Entitlement | Company, feature, state | Checked on every request |

Edits to regulated records create new versions. Earlier versions stay readable, and records are never permanently deleted. They move to a voided state with a recorded reason.

## Authentication and access control

- The identity provider handles passwords, multi-factor authentication, and email verification. Qaabil never stores credentials.

- Roles are company administrator, approver, contributor, and read-only auditor.

- A single permission layer in the application checks the user, role, company, and entitlement on every request. The interface hides actions a user cannot take, but hiding is never the control.

- Role changes and deactivations are recorded in the audit trail.

## Electronic signatures

- To sign, the user must re-authenticate immediately beforehand, within 5 minutes.

- The signature stores the printed name, time, meaning, and a fingerprint of the exact record version signed.

- A signed version is locked. Any later change creates a new version that needs a new signature, and the earlier signed version is preserved.

- Signed records show the signature details on screen, in exports, and in print.

## Audit trail

- Audit entries are written by the same database transaction as the change, so a change cannot commit without its entry.

- The application's database role can add audit entries but cannot update or delete them. Each entry also stores a fingerprint that includes the previous entry's fingerprint, forming a chain for each company, and a scheduled check verifies the chain and raises an alert if it breaks.

- Times come from the server in UTC and are shown in the user's time zone.

- Entries record who, what, when, the values before and after, and the reason where one is required.

- Agent runs and review decisions are audited with the agent name, model version, and prompt version.

## Complaint and CAPA workflow

- Status changes follow a fixed state machine. Closing a complaint or CAPA requires an approval signature from an authorized role, and a CAPA cannot close while any action is open or without a recorded effectiveness check.

- The awareness time is set by the server at receipt and any later change needs a reason.

- A deadline service computes countdowns from the awareness time using the rule set version in force for each applicable market. The product's authorized markets and the country of the event determine which rule sets apply.

- Rule set changes need a signed approval and are audited.

## Email intake

Customers can send complaints into Qaabil by forwarding email. Qaabil never connects to or reads a company's own mailboxes.

- **Address per company.** Each workspace gets its own inbound address on a Qaabil inbound domain, containing a long random token so it cannot be guessed. It is shown in the workspace settings. The customer either forwards complaint emails to it or sets an automatic forwarding rule from its own complaints mailbox.

- **Receiving.** The inbound feature of the email service accepts the message, stores the raw message and attachments unchanged in file storage, and queues a job.

- **Processing job.** The job confirms the address belongs to an active company, scans attachments for malware, enforces size limits, ignores duplicates by message identifier, extracts sender, subject, body, and the original date from the message headers, and creates a draft complaint in an inbox state.

- **Inbox.** A person confirms or discards each draft, with a reason for any discard. Discards are audited, and nothing is permanently deleted. The triage pipeline runs on the draft immediately, so urgent flags appear without waiting for a person.

- **Awareness date.** The system records when Qaabil received the email and the original date from the headers. A person confirms the awareness date and gives a reason if it differs from the time of receipt. \[Rule to be confirmed with the regulatory advisor\]

- **Abuse protection.** Unguessable addresses, an optional sender allow-list, and rate limits.

- **Later phases.** Complaint-specific reply addresses for threading, and optional mailbox connection.

## Triage agent design

The pipeline runs in a fixed order for every new complaint:

1.  **Language check.** Complaints not clearly in English are flagged for manual review and do not continue to the agent.

2.  **Deterministic rules.** Urgent terms, product match, and missing fields are checked. The urgent flag set here cannot be cleared by model output.

3.  **Retrieval.** The system searches only current approved documents, past complaints, and open CAPAs.

4.  **Redaction.** Patient identifiers are removed from the text where configured before anything leaves the system.

5.  **Model call.** The model receives the complaint as untrusted data with fixed instructions, and must return a structured result.

6.  **Output validation.** The result is checked against the schema, and every claim must point to a source passage. Results that fail are rejected and sent for manual review.

7.  **Storage.** The validated result is stored as a suggestion, labeled proposed and not approved.

8.  **Review.** A reviewer accepts, edits, or rejects it, and signing is a separate step.

Safety boundaries: the agent has read-only access to the data it retrieves, it cannot change records, and it cannot send anything outside the system except the redacted request to the model provider. Model version and prompts are fixed in a release and recorded with each run. The agent test set runs automatically on any change to the model, prompts, or retrieval.

## Security controls

- Encryption in transit for all connections and encryption at rest for the database and file storage, using managed keys

- Secrets held in a managed secrets store and never in source code

- Least-privilege access for services and for staff accounts

- Session timeout after inactivity, throttling of repeated sign-in failures, and logging of sign-ins

- Dependency scanning on every release and a penetration test before first customer use

## Backup and recovery

- Automated daily database backups with point-in-time recovery, and versioned file storage

- Backups include the audit trail, and restore tests confirm that records and audit entries return intact

- Retention periods and restore test frequency are open items \[values to be set\]

## Export

Records export as PDF through a background job. Each export includes the record, its signatures, and its audit trail. Lists export as CSV.

## Environments and release

- Separate development, staging, and production environments

- Database changes go through reviewed, versioned migrations

- Every release has a version number shown in the interface and release notes, and passes the validation plan's release criteria before it reaches production
