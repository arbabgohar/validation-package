Rev A (draft), October 2026. Reportability rules and thresholds below must be reviewed by a qualified regulatory affairs professional before use.

## Purpose

Shorten the time from receiving a complaint to a reviewed, documented decision. The agent proposes and a person decides. Nothing the agent produces becomes a record until a named reviewer approves it.

## Scope for v1

In scope:

- Extract structured fields from the complaint text and attachments

- Classify the event type and propose a severity

- Propose a reportability outcome with reasoning and cited sources

- List missing information and draft follow-up questions for the complainant

- Find similar past complaints for the same product

- Suggest whether the complaint should be linked to an existing or new CAPA

Out of scope for v1:

- The final reportability decision

- Drafting or submitting MDR or vigilance reports (a separate agent in v2)

- Closing a complaint or downgrading its severity

- Root cause conclusions

- Contacting complainants or regulators directly

- Any clinical or patient-level medical judgment, and complaints written in languages other than English, which are flagged for manual review

## Inputs

- Complaint text and extracted text from attachments

- Product record: name, version, UDI, intended use

- The customer's own complaint-handling procedure, uploaded as a reference

- Prior complaints for the same product and open CAPAs

- The regulatory rule sets the customer has enabled (for example US medical device reporting, EU vigilance requirements), configured and verified by regulatory affairs

## Outputs

Each run produces one structured suggestion record containing:

- A short summary of the event

- Extracted fields: event date, reporter type, device identifier or lot, stated patient outcome, event description

- Proposed event class: malfunction, injury, death, user error, no device issue, or unclear

- Proposed severity

- Proposed reportability: likely reportable, likely not reportable, or needs RA review, with the reasoning and the source text it relies on

- Confidence as low, medium, or high (categorical, not a percentage)

- Missing information list and drafted follow-up questions

- Similar complaint IDs with a one-line reason for each match

- Suggested CAPA link, if any

- Agent name, model version, and prompt version, stored for the audit trail

## Mandatory human gates

These always go to a person, regardless of confidence:

- Any complaint mentioning death, serious injury, or hospitalization is flagged immediately as urgent and routed to a named reviewer

- The final reportability decision, signed by a reviewer

- Closing a complaint, lowering a severity, or classifying it as no device issue

- Any output with low confidence or insufficient information

- Sending anything outside the system

The system records the awareness date for every complaint and shows a deadline countdown. The exact reporting deadlines come from the configured rule set and are verified by regulatory affairs, not hardcoded from this document.

## Guardrails

- Rules first, model second. Deterministic checks (keywords for death, injury, hospital, missing product match) run before and independently of the model, and the urgent flag cannot be switched off by model output.

- Conservative bias. When unsure between reportable and not reportable, the agent proposes needs RA review. It never proposes not reportable without cited support.

- Cite or say unknown. Every claim points to text in the complaint or a rule source. The agent never guesses missing facts such as a lot number.

- Treat complaint text as untrusted input. Instructions inside a complaint cannot change the agent's behavior, so injection attempts are part of the test set.

- Minimize personal data. Redact patient identifiers before sending text to the model where possible, and confirm the provider's data retention and agreement terms before going live.

- Versioned prompts and settings under change control. Any prompt or model change triggers a re-run of the validation test set.

## Workflow

1.  Complaint arrives and the system stores it with an awareness timestamp.

2.  Rule pre-check runs: urgent keywords, product match, missing fields.

3.  The agent runs and writes a suggestion record.

4.  The reviewer sees the suggestion beside the source text, then accepts, edits, or rejects it with a reason and signs.

5.  The decision updates the complaint, and an audit event records the before and after values.

6.  If the complaint is reportable, the report-drafting workflow (v2) takes over.

## Validation plan for the tool itself

Intended use statement: assistive triage that proposes outputs for human review. It is not a decision maker.

Test set: at least 100 de-identified or synthetic complaints with expected outputs written by a regulatory expert, including ambiguous cases, multi-event complaints, poor-quality text, and prompt-injection attempts.

Starting acceptance criteria, to be agreed with regulatory affairs:

- Every death, serious injury, and hospitalization case in the test set is flagged urgent

- No truly reportable case is proposed as not reportable without being flagged for review

- Key field extraction accuracy meets a threshold agreed per field

- Every proposal includes a citation or an explicit statement that support is missing

Ongoing monitoring: reviewer override rate by field, count of missed urgent flags (target zero), and drift after any model or prompt change. Record all of this in a validation package customers can show an auditor, with Part 11 style controls on records and signatures.

## Success metrics

- Time from receipt to first triage

- Reviewer time saved per complaint

- Override rate by field

- Percentage flagged urgent

- Missed urgent flags (must be zero)

## Open questions

- Decided: version 1 ships with the US rule set only. The EU rule set is a later phase.

- Which model provider, and under what data-handling terms?

- How much should the agent adapt to each customer's own complaint procedure?

- Which languages should be added after v1? Version 1 is English only.

- Who is the named reviewer when a small customer has no full-time regulatory person?

## Suggested build order

1.  Intake, awareness timestamp, and the rule pre-check

2.  The agent and its structured suggestion record

3.  The review screen with signature and rejection reasons

4.  Audit log and the validation test set
