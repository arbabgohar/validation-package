CC-001, Rev A (draft), October 2026. Referenced by VP-001, P11-001, and TP-001. Items in \[brackets\] are open.

## Purpose

This procedure defines how any change to Qaabil is requested, assessed, tested, approved, released, and recorded, so that the validated state of the software is preserved and customers are told about changes that affect them.

## Scope

It applies to changes in:

- Application code, database structure, and configuration

- Infrastructure and hosting settings

- The AI model, prompts, and document retrieval used by the triage agent

- Third-party components and services

- Reportability rule sets delivered by the vendor

- Validation documents

## Roles

- **Change owner:** \[name\]. Raises the change, assesses impact, and makes the change.

- **Independent reviewer:** \[name\]. Reviews the impact analysis, the change, and the test evidence. Where the owner and reviewer are the same person, the record states this and the compensating controls, such as automated tests and a later independent review.

- **Approver:** \[name\]. Approves release.

## Change classes

| Class | Applies to | Minimum assurance |
|----|----|----|
| 1 | Anything that touches electronic signatures, the audit trail, access control and company separation, deadline and rule set logic, backup and retention, or the triage agent. All changes to the model, prompts, or retrieval are Class 1. | Full impact analysis, updated requirements and tests, all High-risk test cases re-run, the agent test set re-run if the agent is affected, independent review, and customer notice before release |
| 2 | Medium-risk functions, such as workflows, records, and exports | Impact analysis, targeted test cases, the full automated suite, and review |
| 3 | Low-risk or cosmetic changes, and documentation | The full automated suite and a recorded check |

When in doubt, the higher class applies.

## Procedure

1.  **Request.** Record the change in the tracker with a unique ID, a description, the reason, and the requested date.

2.  **Classify.** Assign the class with a short rationale.

3.  **Impact analysis.** List the requirements, risks, design sections, and test cases affected, and the documents that need a new revision letter. Add or update requirements and risks if the change introduces new behavior.

4.  **Make the change.** Work in a separate branch, and have every change reviewed before it is merged.

5.  **Test.** Run the automated suite and the test cases the class requires, in the staging environment, and record the results and evidence.

6.  **Approve.** The approver confirms the evidence, the updated documents, and the release criteria in VP-001.

7.  **Release.** Give the release a version number, write release notes, take a backup, and keep a tested rollback plan.

8.  **Notify.** For Class 1 changes, tell customers before release \[notice period to be set\], what changed, and what they may need to re-verify. Class 2 changes appear in the release notes.

9.  **Verify and close.** Check the release in production against a short list of critical checks, record the result, and close the change.

## Emergency changes

A critical security fix, or a fix for a defect that risks missed urgent flags or data loss, may follow a shortened path:

- The change owner and one other person agree it is an emergency, and the reason is recorded.

- The change is tested as far as time allows, and the full class requirements are completed afterward.

- A retrospective review takes place within \[period\], and affected customers are told promptly.

## Rollback

Every release has a rollback plan. Database changes are reversible or are preceded by a backup that has been confirmed good. A rollback is itself a change and is recorded.

## Documents

When a controlled document changes, its revision letter increases (Rev A, Rev B, and so on). Superseded revisions are kept and marked as superseded. Traceability (TM-001) is updated with every change that affects requirements, risks, design, or tests.

## Records

The change record holds: ID, description, class, impact analysis, reviews, test evidence, approvals, release version, customer notification, and closure. Records are retained for \[period\].

## Review

This procedure is reviewed at least once a year and after any incident that points to a gap in it.
